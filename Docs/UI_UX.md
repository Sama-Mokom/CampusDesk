# CampusDesk — UI/UX & Design

## Design Origin

The frontend UI was originally generated by **v0** (Vercel's AI design tool) from a detailed prompt specifying:
- Three role-based dashboards (Student, Staff, Admin) shown in a tabbed preview
- Design language: "clean, minimal, institutional feel... think university portal, not a startup SaaS"
- Neutral palette (whites, grays, one accent color — slate blue)
- Card-based layouts
- No dark mode requirement

This original design direction has been preserved throughout backend integration — the explicit instruction to the Cursor Agent refactoring pass was: **"Do not redesign the UI — preserve the existing design language, layout patterns, and component style. Your job is purely structural."**

## Layout Principles

- Card-based layouts for requests, stages, and list items throughout
- Status badges with consistent colour coding across the app:
  - `draft` → gray
  - `pending` → yellow/amber
  - `in_review` → blue
  - `forwarded` → purple
  - `ready` → teal/green
  - `collected` → green (darker)
  - `rejected` → red
  - `approved` (stage-level) → green

## Application Shell (`App.vue`)

The root `App.vue` renders:
- A sticky top header with the CampusDesk logo, user name/role label, `NotificationBell`, and a Log Out button
- A separate auth-mode header (logo only, no user controls) shown on `/login` and `/register`
- The main `<router-view>` with a fade transition between routes
- A footer with quick links and a live-clock system status indicator

The header's Log Out button calls `clearAuth()` (clears localStorage) and navigates to `/login`. Note: this does NOT revoke the Sanctum token on the server (known bug — see KNOWN_ISSUES.md).

## Key Screens

### Login / Register
- Simple centered forms
- Register includes cascading dropdowns: faculty → department (filtered by faculty) → programme (filtered by faculty) → level
- Dropdowns populated from `GET /api/faculties`, `GET /api/departments`, `GET /api/programmes` on mount

### Student Dashboard (`StudentDashboard.vue`)
- Header: greeting with student name, matricule badge, faculty/department names, level badge
- Stats strip: total requests count, pending count, ready-for-collection count
- New request form: type dropdown, description textarea, multi-file attachment input
- Recent requests list: cards showing type, status badge, date, click-to-expand detail
- Request detail modal: description, status badge, reopened indicator, attachments (via `DocumentViewer`), vertical stage timeline, collapsible status history log
- Conditional action buttons:
  - "Reopen Request" shown if status is `rejected` — calls the API, disables while in flight, then updates the detail/list state and displays success or error feedback
  - "Mark as Collected" shown if status is `ready` and calls the authenticated collection endpoint

### Staff Dashboard (`StaffDashboard.vue`)
- Header: staff name, staff ID, primary department name
- Department tabs/switcher (if staff belongs to multiple departments)
- Stats strip: unclaimed count, active cases count, resolved today count
- Unclaimed queue: cards with student name/matricule/level, request type, description (truncated), "Pick Up" button
- My Active Cases: claimed stages with "Update Status" button opening a resolve modal
- Resolve modal: approve/reject select (maps to `approved`/`rejected`), conditional required staff note textarea
- Request detail modal (shared pattern): full stage timeline + attachments before deciding

### Department Admin View (`DeptAdminView.vue`)
- Uses the primary-department API for stage statistics, staff, and claimability
- Allows reassignment of claimed, in-review stages to assigned staff

### Super Admin View (`SuperAdminView.vue` + `AdminDashboard.vue`)
- `SuperAdminView.vue` wraps the API-backed dashboard
- Displays system statistics, recent status activity, paginated request cards and filters, user management, reference-data tabs, and paginated request/stage status history
- The request modal reuses `RequestTimeline` and the protected `DocumentViewer`; rejected requests expose the existing reopen action
- Staff user forms offer faculty-grouped department search, selected memberships, and a primary-department selector

## Frontend data sources

The active dashboards and notification bell load data through `Frontend/src/services/` and the shared Axios client. Authentication state is managed by `useAuth.ts`; no in-memory mock-data composable is retained.

## Document Viewer Pattern (Secure Blob)

`DocumentViewer.vue` receives an array of `Attachment` objects and handles:
- Clicking an attachment button fetches the file via `GET /api/attachments/{id}` with Axios `responseType: 'blob'` (Bearer token attached automatically)
- The blob is displayed using `URL.createObjectURL(blob)` in an `<img>` (images) or `<iframe>` (PDFs)
- Unsupported file types show a download fallback
- Clicking the active attachment again collapses the viewer (toggle behaviour)
- An "Open in new tab" button opens the blob URL in a new window
- Deselecting the file calls `URL.revokeObjectURL()` to free memory

Unit tests for `DocumentViewer.vue` exist in `src/components/__tests__/DocumentViewer.spec.ts`.

## Empty / Loading / Error States

- **Empty state:** "You have no requests yet." shown when student has zero requests
- **Loading states:** A `loading` ref gates rendering in each wired component during `onMounted` async fetches
- **Error states:** Inline error messages (`error.value`) shown on failed API calls. 422 validation errors surface the backend's specific field messages. Generic fallback message shown for other errors.

## Accessibility, Internationalization, Mobile

- **Accessibility:** Not explicitly tested or audited. DaisyUI/Tailwind provide some baseline accessibility via semantic HTML and ARIA on their component primitives, but no ARIA audit, keyboard navigation testing, or screen reader testing has been performed.
- **Internationalization:** Not implemented. All UI strings are English only. No i18n library is installed.
- **Mobile:** Tailwind's responsive utilities are present (from the v0 scaffold). No explicit mobile-specific testing was performed. The layout uses `max-w-7xl mx-auto` containers and responsive grid columns (`grid-cols-1 md:grid-cols-X`) — it should be usable on mobile but is not formally tested.
